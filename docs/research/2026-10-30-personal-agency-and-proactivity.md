# DSH Dot：Personal Agency 一手研究与可执行方向

研究时间：2026-10-30。依据厂商公开产品文档、开源仓库与本机项目代码；官方能力描述不等于已独立复现，不推测内部算法、隐私实现或用户规模。当前进展见 canonical `.agent/memory/progress.md`，本文件不改变任何账户、权限、计划或运行时。

## 一句话结论

有用的主动性不是更频繁地发日报，而是围绕本人已明确交办的持续目标，识别一件值得推动的变化，结合来源与上下文准备可审阅的下一步，在适当时机出现；事情已处理、无变化、来源缺失或授权不确定时，不要猜测或骚扰。阶段内可以复用现有个人回顾事项账本与 host 唤醒能力，不需要重建通道和个人数据栈。

## 先识别产品：什么已确认

### OpenAI dots，而不是一个被证实名为“Codex Dot”的单独产品

[Meet dots](https://developers.openai.com/codex/dots) 和 [Tasks and memory](https://developers.openai.com/codex/dots/tasks-and-memory) 描述的是 OpenAI 的个人 dot：跨会话承担持续责任，可以根据工作进展决定暂停与何时继续；还支持用户明确的定时任务以及连接服务支持的事件。连接一个服务本身不等于开始监控。

它会使用相关对话、记忆及自己的持续笔记；主动研究读取已授权信息，研究本身不能发消息、修改连接应用或控制电脑；后续行动适用原权限和审批。用户可以指定值得通知的变化和渠道，停止当前任务与取消周期任务是独立操作。[Control your dot](https://developers.openai.com/codex/dots/controls)。官方 [发布文章](https://openai.com/index/introducing-dots/) 给出“发现未开发票、准备后由用户批准发送”的例子，属于厂商叙述，不应推断其调度、排序或内部数据结构。用户此前描述的 Dot 主动提醒是该用户的使用体验，不足以证明提醒的内部触发机制。

真实运行条件有差异：OpenAI dot 官方称其有云端计算机，电脑关闭仍可进行云端工作；本项目目前依赖本机 Host 与已有微信通道，不能把本机原型宣传成云端全天候服务。

### Meta Muse：目标与持续行动

Meta [Introducing Muse](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/) 将 Muse 定义为个人 AI agent：用户提出目标后协助制订计划，跨授权应用后台推进；工作有变化或需要许可时回来。官方称 Muse 可记住用户认为重要的事项，用户可要求忘记，决定连接范围及权限；发送邮件、购买等敏感动作前请求授权。Meta 使用云端隔离虚拟机和独立安全组件；这些是其架构，不是本地 Dot 的既有能力，也不能据其文案推断实际内部排序或质量表现。[Muse 官方功能页](https://ai.meta.com/muse/)。

可借鉴的重点是“目标→持续工作→结果或决策”而非开放更多功能菜单：一条跟进应说明它服务哪件事、为何现在出现、用户下一步能做什么。

### xAI Grok Bot：持续责任、事件与可见产物

[xAI 产品介绍](https://x.ai/news/introducing-grok-bot) 称 Grok Bot 是持续运行的 agent，可以跨授权工具工作、记住协作偏好、跟进停滞线程和交接；把工作交付到实际工具，并在需要判断/批准时联系用户。[官方设计文章](https://x.ai/news/designing-grok-bot) 描述 Routine 可由计划或受支持事件触发，执行记录和例外在时间线中可见；工具与技能可共享，但个体 Bot 的记忆和周期任务保留角色边界。文章所列事件属于产品设计能力，不证明 DSH 已有对应的 webhook 或云端运行能力。

对 Dot 的启发：让用户看到“正在等什么/接下来做什么/是否需要我”，而不是只看到机器是否在线；同一件事应可从简报自然继续，成果应标明是真实执行、建议还是待确认。

## 本项目已有能力：先复用，不假装从零建设

截至当前项目进度文件记录，本机已有每天/每周个人回顾和 AI 日报的已设计划；来源与授权保持原样。当前本地安装及真实私人资料手机新预览仍以进度文件为准；自然跨日、跨周、休眠重连及长期体验没有由这些代码或合成测试证明。

- `src/personal-review-ledger.js` 已有证据、事项 ID / 别名、`revision` / `notifiedRevision`、优先级、截至时间及来源可信度，按已处理 / 暂缓 / 不再提醒抑制；一次每日最多 3 项、每周最多 5 项；没变化、缺失和失败有独立语义。
- `src/personal-review.js` 已有显式配置、预览、一次执行、暂停、恢复、取消与反馈，并记录调度发生和投递状态；已报告发送不等于手机收到或已读。
- `src/news-service.js` 已有按用户关注点选择、近 24 小时窗口、已投文章去重及来源可用性统计；进度文件记录当前公开 RSS 列表 92 个，这并不保证每次成功覆盖或产生 10 条。
- `vendor/proactive` 与 `src/project-followup.js` 已有调度、免打扰、结果静默、授权范围和投递回执方面的基础；评估具体版本和当前分支后再复用，不能假设现有 Host 或微信链路等同手机完成验收。

## 下一步：围绕一个可验证闭环做增量

**建议选一个代表性目标，运行已有每日个人回顾时，把“事情还在推进吗”做成有证据、可继续的跟进；在已存在计划上改善，而不是额外悄悄开启监控。**

1. **目标与关联：** 将“用户明确交办的目标/已知项目”和既有 review item 关联；保留来源、最后核实时间、未完成/未知的区别。只使用已启用且此次计划明确授权的资料。没有明确用户目标时，候选只标为建议，不能自动替用户承诺或创建任务。
2. **变化而非复述：** 当前账本已有 identity、revision、due、handled/snoozed/dismissed；基于它比较上一轮已确认的事实与本轮来源，优先突出新增阻塞、负责人/期限变化、一个真实即将到来的会议或明确等待的回复。来源失败、查询范围不足或滴答只返回未完成项目时，显示“未核实/覆盖不足”，不能反向推断任务完成。
3. **下一步可接住：** 每条只给一项与证据相符的下一步，如“先核对 X，然后整理会议前要问的两个问题”；引用和更新时间留得下。用户明确要求时复用现有安全项目能力生成草稿或只读检查；不能声称交办已执行、原项目会话已运行、消息已发送或对方已收到。
4. **节制触达：** 复用已有去重、用户反馈、安静时段与计划；例行低优先级变化合并既定回顾，无新增或已暂缓时静默，明确用户设置的提醒按现有语义处理。不同于固定日报，事件/时间触发式额外提醒需先有明确授权与真实事件证据，不暗中创建新周期。
5. **可控回路：** 用户可自然表达“已处理”“明天再说”“别再提醒”，优先复用现有反馈语义而非重新设计数据库；变更来源并不自动推翻本人已处理/不提醒。准备工作不自动对外发送，结果状态区分读取、生成、任务接收、实际完成、通道接受、手机收到。

可验收样例（全部使用合成资料）：一封有明确截止时间的邮件 + 日历中同项目会议 + 一个已关注项目，首次回顾指出一项需要在会前核实的事及来源；第二次无变化保持安静；对方邮件真正更新时仅提示变更；用户暂缓或取消后不再提醒；来源断线显示未知而不是无事；明确未发送时不吞事项，投递结果不确定时不盲重发。随后再在用户同意的实际范围内做一次真实手机体验确认。

## 不应误称的差距

目前无证据表明 DSH Dot 有 Muse/Grok 的云端独立电脑、任意事件监听、持续浏览、跨任务自主执行或已验证的主动学习。用户现有计划和授权具有明确范围；从本机每日回顾升级为全天候的自主发现需要新的产品与运行时设计。用户实际手机能否收全、排版是否合适以及长期低打扰性，仍由真实验证决定。
