# 跟手：双 agent 对话层设计（B）

目标手感：你发一条消息，它立刻有回响；后台继续做事；你可以随时插话，插话也有回响；真正干活的那条路径不会假装已经完成。

这不是给 Dot 加一个工具能解决的。工具插件的调用者是模型，它决定不了"谁先回话"。这份文档记录目标、现状、缺口和桥接层原型的落点，供评审后再动手。

## 目标行为（按优先级）

1. **秒回**：消息进来先给一句有内容的回响（不是固定模板，理想是按上一轮上下文生成）。
2. **不阻塞**：回响之后主流程继续执行，不因为回响而中断或重跑。
3. **插话有回响**：执行中用户继续发消息，每条都要被确认，并按语义决定是排队还是修正方向。
4. **执行者不直连用户**：真正干活的 agent 只产出结果，由回响方转述；避免两处同时下结论。
5. **失败不冒充成功**：结果不确定时明确说"还没确认"，不重放。

## 现状（0.34.0）

- 已有：微信消息 claim 后先发一条固定回执（`index.js` 的 `quickAck`，家庭入口走 Family 桥、独立微信走站点桥，同消息去重）。这是第 1 条的最小实现，内容还是模板。
- 已有：插话进入宿主队列（Harness 自身行为），但**没有"每条插话都有回响"**。
- 已有：交办结果由 `taskResults` 回传原会话，可区分完成/无文本/失败/超时。
- 没有：chat agent 与 agentic agent 的分离；没有 steering 提权接口。

## 缺口（按证据）

1. **宿主没有对话层原语**：本机 Harness `0.2.2-rc.1` 的可读 SDK 里没有 steering/双写接口（`app.asar` 为打包产物，`app.asar.unpacked` 只含四个包）。因此"同一条消息双写两个 agent、chat 可把队列提成 steering"不能在插件层实现。
2. **回复通道不对称**：Dot 能通过桥发消息，但不能决定宿主对话的回复由谁发出。要做到"执行者永不直连用户"，只能在桥接层拦住出站回复并改写。
3. **回响内容质量**：模板回执只能解决"有回响"，解决不了"回响有用"。

## 桥接层原型方案（可行且不动宿主）

落点在 `vendor/dsh-wechat/dist/bridge/bridge.js`：

- 入站：`onMessage`（约 1049 行）之后、把消息注入宿主之前，先取一条"回响"：优先用上一轮结果摘要 + 本轮意图做一句短回复；失败则退化为固定回执，保证一定发出。
- 出站：宿主回复到达后，若本轮已经发过回响，则把结果作为**第二条**消息发出，并标注"结果"；不拼接、不改写。
- 插话：入站分支若同一会话已有在跑的轮次，则回响改为"收到，我正在做上一件事，你的这条我记下了"，并把消息按原文注入宿主队列（当前行为不变）。
- 提权：宿主没有 steering 接口，**先不做**；等宿主暴露后再接，文档明确标注未实现，不用"看起来像"的方式假造。

验收方式：真实手机发一条 → 3 秒内收到回响 → 结果随后到达；执行中再发一条 → 两条都有回响；结果不确定时表达为"尚未确认"。

## 不做什么

- 不在插件里伪造 chat/agentic 两个 agent 的假象。
- 不把固定模板说成"AI 回响"。
- 不在没有任何交接证据时宣称"跟手已实现"。
