# Context、资讯与主动跟进：现状审计及下一步最小闭环

日期：2026-10-20，America/Mexico_City。

状态：只读源码审计与建议，不是已实施方案。本轮没有读取个人账号内容，没有抓取真实新闻、调用模型、运行重测试、操作 UI、创建计划或发送微信。仅新增本文件；不改当前运行实例、旧计划、配置、网络或其他 Agent 的代码。

后续实施记录：本分支依 root 冻结的范围，只实现了「本次显式关注点的资讯预览」和「按 UTC 日期轮换 RSS 扫描起点」两项。关注点最终上限为 8 条、每条 80 字符、总计 400 字符，没有实现排除主题、保存兴趣、项目变化卡或统一发送预算。下方现状与行号保留的是实施前 `c70928c` 的审计快照，不代表新增能力尚未存在；合成测试通过也不等于真实模型质量或手机收件验收。

## 一句话结论

当前已经有「公开资讯最多 3 篇重点＋7 篇速览」「固定项目日报」「按变化的只读项目跟进」三条独立路径。最影响日常价值的不是少推了几条，而是资讯不知道用户正在做什么、固定项目日报仍以来源摘录为主，以及三条路径没有共同的用户级打扰预算。下一轮先做一份有明确关注主题、能解释相关理由的预览，再把本地项目简报改成有证据的变化卡；最后接共享发送门，不自动增加推送。

## 2. 真正影响使用的缺口

### A. 泛用资讯还没有变成「对我有用的资讯」

1. 新闻模型输入只有时间和公开文章字段。`selectArticles`/`summarizeArticles` 没有主题偏好、当前目标、反馈或用户角色参数；宿主接线也没有引入项目记忆或个人 context。当前「值得关注」针对泛 AI Builder，不能解释与某个用户项目的具体关系。证据：`news-model.js` 27–48、96–101、184–205；`index.js` 154–159；`docs/news.md` 23 行明确说明不附带本地项目记忆。
2. 清单按照固定顺序从头扫描，45 秒截止后保留成功项。若部分来源持续慢，排在后面的来源可能反复未及扫描；这是扫描策略偏差，不是这些博客都失效。证据：`news-feeds.js` 400–428，特别是共享 `next++` 和固定传入数组。
3. 只有 URL 级去重；同一发布事件的不同 URL 依赖模型提示词去重。没有来源数量上限或事件级重复证据，也没有「选入/不选入」的简短原因。证据：`news-feeds.js` 431–436、`news-model.js` 98、`news-service.js` 40–44。
4. 正文抽取优先 `article/main`，否则整页转文本，100 字符即可能达到正文门槛。没有为抽取方式、登录页/导航噪声和正文覆盖率提供质量报告。因此 `coverage=article` 只能表示取到有界网页文字。证据：`news-feeds.js` 448–451；来源说明 31–34 行已保留边界。
5. 失败信息在最终状态中被压缩成「本次失败」。来源失败、无合适文章、模型格式失败和原绑定不可用的恢复动作不同，但用户可能看不出下一步该做什么。证据：`news-service.js` 14、39、48–53；`index.js` 477 的统一错误回复。

### B. 项目「资料可读」与「能主动帮我判断」仍分开

1. 固定项目日报直接调用 `digest()` 的 `wechatText`。摘要视图主要是文件/事件摘录，固定文件前三百字无法保证关键阻塞在可见范围。完整分析材料已存在于 `detail=analysis`，按变化跟进也在使用，但固定日报没有复用这一判断层。证据：`service.js` 213–245、397–398；`project-followup.js` 118。
2. 按变化跟进有 `lastReviewedAt`，提示模型忽略测试调度、状态查询及上一轮汇报，并维护成功读取的证据。但实质变化/无变化的判断主要靠模型，并不是确定性的内容差异账本。证据：`project-followup.js` 117–118、177–180、225–235。
3. `personal_context` 只有显式 `query/brief`，不会自动订阅或增量保存来源。主动跟进的硬工具白名单甚至明确禁止使用 `personal_context`。因此不能把「资料已连接」宣传为「日历/滴答/笔记变更已在主动盯」。证据：`context-service.js` 34–36；`project-followup.js` 165–166。
4. 多来源 brief 把相同查询参数交给不同来源，而各来源支持的范围不同；不兼容时会诚实返回 unavailable，不会删掉条件扫全账号，但组合体验还不顺。下一版应给出每个来源的实际读取范围和不能应用的筛选条件，而不是把授权扩大。证据：`context-service.js` 35；`context-contracts.js` 的逐操作参数白名单。

### C. 需要统一打扰治理，而不是增加推送

1. 周期项目跟进沿用本机时区 23:00–08:00 免打扰，重启过期策略为 drop；默认预算每个项目独立实例 50 条/UTC 日、60 次唤醒/小时。这里的 50/60 是库上限，不能当成推荐用户接收量，更不是所有项目加总后的用户级限制。证据：`project-followup.js` 210、243；`vendor/proactive/lib/config.js` 13–24；`vendor/proactive/lib/scheduler.js` 166–179。
2. 新闻每日计划和固定项目日报分别有自己的每日领取/去重记录，没有复用跟进的静默门或跨类型预算。用户同时开三条路径时，可能收到三类相近消息。代码本身没有「一个关注事项只通知一次」的统一状态。证据：`news-service.js` 9–10、60；`service.js` 391–400；README 73 行已披露计划彼此独立。
3. 微信每个互动窗口最多连续主动推送 10 条，是通道约束，不能用重绑、自动复位或多发消息绕过。项目的内部 50 条上限没有改变这个约束。证据：README 71 行；`docs/news.md` 27 行。
4. 用户明确设置的某个时间提醒、主动询问后的答复和低优先级背景更新必须区分；不能简单给所有消息套「夜间不发」，也不能以「已设日报」为由自动增加发送时段。现有一次性项目检查是显式授权，允许绕过周期免打扰；这项语义应保留。证据：`project-followup.js` 227、277，与 314 对照。

## 3. 建议下一轮只做的三个小改动

### 优先 1：有关注主题的资讯预览

目标：用户一句话「我最近在做 DeepSeek 插件，关心 Agent 产品与生态，预览一期」后，结果能说明为什么与这些主题相关。默认仍不发送、不建计划。

最小实现边界：

- 新增最多 3 条、总计不超过 400 字的显式阅读关注点，以及少量排除主题。只接受用户自己提供/确认的文字；不从 flomo 画像推断、不自动读取账号、不自动遍历项目。
- 同一 pipeline 接收独立的 `readerFocus`，只影响筛选与「为什么相关」。RSS/网页仍是非可信引用数据，不拥有授权。
- 相关理由必须能回指具体关注点和已提供文章事实。不要把泛「提升效率」当个性化；完全不相关的内容可少选。
- 先只做 preview；存储偏好须有明确修改动作与来源标记。要把本地项目目标或外部 context 加入模型输入，另做明确选择与最小投影，不能偷偷改变当前「仅公开文章进入资讯模型」的边界。
- 源扫描保持既有时间与并发上限，可按日期确定性轮换起点，记录实际扫描覆盖；不增加来源或私网访问。

验收：合成主题 A/B 用同一公开候选，排序/理由随关注点改变且有出处；未给偏好时保持当前泛用行为；未知个人信息不出现；RSS-only 不变成「已读全文」；没有发送、计划或账号读取副作用。

### 优先 2：把一份项目日报变成有证据的变化卡

目标：只选一个已有授权本地项目，先预览「新增变化 / 当前阻塞 / 建议下一步」，每条带来源和时间；没有变化能简短说明或静默，而不是再抄一遍 README。

最小实现边界：

- 复用现有 `memory`＋`digest(detail=analysis)` 和同一份提炼逻辑；不要扩大固定项目文件范围，不扫描历史全库，不放开主动跟进的写/派工权限。
- 区分文件更新、助手声称完成、执行证明、用户验收。无变化判定保留上次成功读取的水位；对来源缺失/截断只能说未知。
- 增加一个可解释的变化判据：来源 ID/内容摘要的指纹变化只触发重新判断，不能单凭 mtime 或 hash 改变就断言业务有进展。
- 首次概览与以后增量分开；已报过的相同阻塞不反复提醒，阻塞实质改变再报告。
- 先让本地预览及合成差异测试通过，再把现有固定项目日报切到同一摘要层；不新建第二条默认计划。

验收：只改调度记录应静默；真实新增阻塞应出现并标来源；相同阻塞下一轮不重复；移除/截断来源不能当作任务完成；暂停、取消、换绑不继续读或回传。

### 优先 3：同一个人只有一个主动发送门

目标：相同变化不被新闻、项目日报和周期跟进分别打扰；统一显示待发送、静默、额度、排队、失败和未知回执。

最小实现边界：

- 第一版先加只读「今天有哪些计划/消息、为什么没有发」预览与分类，暴露已有事实，不自动改任何计划。
- 后续共享发送门按原微信绑定划分，使用本地日、用户明确的免打扰时段和主动消息预算；不提高当前发送量、不自动增加新时段。
- 定时资讯可以占一条汇总，低优先级项目变化优先合并；显式提醒、显式交办完成答复另有语义，不能吞掉。不要把所有消息机械合并成一大坨。
- 通道已排队/结果不确定按保守占额处理，不重复投递；强约束 10 条窗口，不能绕过。
- 记录选择「发/合并/静默/等下一时段」的原因；只保存最小来源指纹和发送状态，避免把私人邮件、笔记正文复制到公共资讯状态或新的总账。

验收：同一变化跨两条路径最多产生一份用户可见汇报；夜间低优先级变化不增发；明确提醒保留原语义；未知发送不重投；关闭资讯不影响项目提醒；切换账号/绑定时计划不迁移。

## 4. 建议最先跑的一条闭环

使用合成的关注点「DeepSeek 插件与创作者生态」及公开候选，完成一次**个性化资讯预览**；旁边列一张**所选项目变化卡预览**，明确各自来源与更新时间，再给出「如果现在启用，会在哪个已授权时段发几条」的**计划预览**。整轮零微信发送、零私人账号读取、零新计划。

用户醒后先评估「哪些内容真能用、为什么相关、是否有重复打扰」。通过后再沿用原微信绑定做一次真实收件确认；无须让用户为每个来源反复发送测试命令。此处不把未执行的测试、用户未看的预览或已有桥接回执写成已验收。

## 5. 这轮不做

- 不把 92 补成 100 个来源来满足宣传数字，不使用未核实的 Karpathy 背书。
- 不自动接入所有已配置账号，不默认把私人 context 塞进新闻模型，不从外部画像推断个人事实。
- 不增加推送上限、不绕微信窗口、不在用户睡觉时发实验消息或创建真实周期计划。
- 不承诺云端持续在线；本机与 Harness 在线仍是现有实现条件。
- 不把安全/幂等测试通过等同资讯质量、真实持续使用或手机交付已验收。
